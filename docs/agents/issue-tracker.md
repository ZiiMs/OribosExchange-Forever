# Issue tracker: Beads

Issues for this repo live in the **Beads** database managed by the `bd` CLI. Storage is embedded Dolt under `.beads/embeddeddolt/oe`; the project prefix is `oe`, so ids look like `oe-a3f2dd`.

The database is gitignored, and `.beads/issues.jsonl` is a passive export, not the source of truth. Cross-machine sync is `bd dolt push` / `bd dolt pull`, which writes `refs/dolt/data` on `origin` and leaves `refs/heads/*` alone.

## Conventions

- One issue per ticket. Types: `bug`, `feature`, `task`, `chore`, `epic`, `spike`, `decision`.
- Priorities: `0` critical, `1` high, `2` medium (default), `3` low, `4` backlog.
- A spec is one issue whose body is the spec. The tickets it produces are child issues of it (`--parent <spec-id>`).
- Blocking is native: `bd dep add <blocked-id> <blocker-id>`. Use `discovered-from:<id>` when one issue turns up another.
- Triage state lives in labels (see `triage-labels.md`); `bd` status stays operational (`open`, `in_progress`, `blocked`, `closed`).
- Add context with `bd comment <id> "..."` rather than rewriting the description in place.

## When a skill says "publish to the issue tracker"

```bash
bd create "<title>" -t <type> -p <0-4> -l <labels> -d "<body>"
```

For a multi-paragraph body (a spec or agent brief), write it to a file and pass `--body-file <path>`; use `--acceptance` for acceptance criteria. Print the returned id.

For a ticket produced from an existing issue, pass `--parent <parent-id>` so it becomes a child issue.

## When a skill says "fetch the relevant ticket"

```bash
bd show <id>          # description, labels, dependencies
bd comments <id>      # conversation
```

Beads ids are prefixed `oe-`. A bare `#42` is a GitHub issue or PR in this repo, not a Beads id: resolve it with `gh issue view 42` or `gh pr view 42` when the user gives it in that form.

External PRs are not a triage request surface. Triage covers Beads issues only.

## Triage operations

- Untriaged: `bd list --status open --no-labels`
- Waiting on the reporter: `bd list -l needs-info`
- Ready for an agent: `bd list --ready -l ready-for-agent`
- Waiting on a human: `bd list -l ready-for-human`
- Move state: `bd label remove <id> <old-state>` then `bd label add <id> <new-state>`
- Categorise with the issue type: `bd update <id> -t bug` or `-t feature`. When a skill asks for a `bug` or `enhancement` label, add it as a label too.
- Wontfix: post the reason as a comment, then `bd close <id> --reason "<why>"`.

Every comment posted during triage starts with `> *This was generated by AI during triage.*`

## Wayfinding operations

Used by `/wayfinder`.

- **Map**: one issue labelled `wayfinder:map`. Its body holds Destination, Notes, Decisions so far, Not yet specified, Out of scope.
- **Child ticket**: `bd create "<title>" --parent <map-id> -l wayfinder:<type>`, where the type is `research`, `prototype`, `grilling` or `task`. The body holds `## Question`.
- **Blocking**: `bd dep add <ticket-id> <blocker-id>`.
- **Frontier**: `bd list --parent <map-id> --ready --no-assignee --status open --sort priority` — open, unblocked, unclaimed children. Priority first, then oldest.
- **Claim**: `bd update <id> --claim` sets the assignee to you. An open, unassigned ticket is unclaimed.
- **Resolve**: `bd comment <id> "## Answer ..."` then `bd close <id>`. Append a one-line pointer to the ticket's answer under the map's Decisions so far: `bd show <map-id> --json`, edit the description, and write it back with `bd update <map-id> --body-file <path>`.

Wayfinder map and ticket bodies are markdown; keep them in the issue description so the map stays a single artifact.
